# OpenFrame — design spec

Every decision here was made with the user. If an implementation detail forces a change, stop, explain the options, and let the user decide. Sections describe the system **as built** where it exists, and the plan where it doesn't (marked *later* or *Phase N*). Decisions are dated in §25.

## 1. Goals and scope

A reliable, subscription-free appliance on the existing frame: a photo and video slideshow plus any number of color-coded Google calendars, with clock and weather, an easy settings UI, and (later) Home Assistant and Immich integration. It matches Frameo's everyday experience minus its social/cloud features, with multiple calendars as the key improvement.

**Version 1** (Phases 0–8) is the point where the user can disable Frameo and live with OpenFrame day to day: slideshow from internal storage and SD/USB; all calendars with colors, Frameo-style day panel and full-screen calendar; clock and weather; three presets; settings with backups; upload page and iPhone Shortcut; warnings and offline icon; start on boot, sleep schedules, crash recovery.

**After version 1**, in order: per-photo menu; photo caption (date, location, comment); text styling, weather display options and dark mode; videos; layout editor and multiple pages; Home Assistant; SD/USB import/export; Immich (§24).

Ideas from Frameo, not scheduled: **collage mode** (two portrait photos side by side), **countdowns** to calendar events on the slideshow, **albums** with a picker in the quick menu (`docs/frameo-reference.md`).

Not included: Frameo friends/codes, reactions, the Frameo app, Frameo+ cloud, importing existing Frameo photos (`/sdcard/frameo_files`, user said no for now), two-way calendar editing, HA logic running on the frame.

## 2. Hard requirements

- Works with **no internet, no HA, no NAS**: cached calendars, cached weather, and local media keep displaying.
- Starts on boot; fully usable by touch; recovers from crashes on its own.
- Light on memory (~590 MB free at idle). One main WebView; images pre-resized.
- Everything configurable in settings, on the frame and from a phone/PC browser on the LAN. Other devices need the **web access PIN** (§16a); the frame itself never asks.
- Reversible: Frameo stays installed; OpenFrame can be uninstalled at any time.

## 3. Architecture

A thin native Kotlin shell hosts a local web UI in one full-screen WebView. The UI talks to the shell over HTTP on `127.0.0.1:8080` (same origin).

Shell (`app/src/main/java/app/openframe/`):

| Class | Role |
|---|---|
| `MainActivity` | Full-screen WebView, `FLAG_KEEP_SCREEN_ON`, follows system orientation. Adds `OpenFrameShell` to the user agent. Navigation is limited to the local server. Reports touches for sleep hours. Reached as HOME through the `.HomeActivity` alias (§18). |
| `LocalServer` | NanoHTTPD on `0.0.0.0:8080`: UI files, JSON API, media, uploads; PIN gate (§16a). |
| `MediaIndexer`, `MediaDb`, `ImageProcessor` | Index `FrameMedia/` and removable volumes, display copies, face crop, SQLite `media.db` (§5–6). |

| `Slideshow` | Order, shuffle deck, history; survives reloads and reboots (§7). |
| `CalendarSync`, `IcsTrimmer` | Download, cache and trim ICS feeds (§10). |
| `WeatherSync` | Open-Meteo forecast and place search (§12). |
| `ConfigStore`, `ConfigHistory`, `ConfigBackup`, `SecretsStore` | Validated `config.json`, snapshots, restore/export/import, `secrets.json` (§16). |
| `WebAccess`, `PinGuard` | Web access PIN, sessions, upload key (§16a, §17). |
| `WarningRules`, `WarningCenter` | What counts as a warning; popup dismissals (§13). |
| `UploadReceiver`, `UploadNames` | `POST /api/upload` (§17). |
| `Library` | Library thumbnails, delete to trash / hide, restore, purge (§15). |
| `MediaEdits` | Validates per-photo fit, position, and comment (`PATCH /api/media/<id>`, §15). |
| `PlaceIndex`, `Places` | Offline city names for photo GPS, place search, places left out of the caption (§8). |
| `SystemInfo`, `Diagnostics` | Settings → System facts and frame set-up checks; storage diagnostics over Wi-Fi. |
| `PowerController`, `SleepSchedule`, `SleepAdminReceiver`, `PowerAlarmReceiver`, `PowerOff` | Sleep and wake, schedules, brightness, nightly UI reload; Shut down / Restart through `su` (§18). |
| `FrameService` | Foreground service while the UI exists: keeps the night wake lock effective (§18). |
| `SoundController` | Main volume: Android's media and system sounds volumes, click sounds, test beep (§6); reminder chimes and the reminders (alarm) volume (§11). |

Recovery note (measured): the frame is `ro.config.low_ram=true`, so WebView runs **single-process** (renderer inside the app). A renderer crash kills the app process, so `onRenderProcessGone` won't fire; recovery is a process restart (`CrashGuard`, §18).

Web UI (`app/src/main/assets/web/`, no build step): `app.js` (layout renderer, quick menu, pages), `layout-editor.js` + `.css` (Phase 13c), `autocolor.js`, `fonts.css` + `fonts/`, `theme.js` + `dark.css`, `photo-menu.js` (photo actions, position and comment editors, Undo), `caption.js`, `slideshow.js`, `clock.js`, `calendar-day.js`, `calendar-full.js` + `calendar-timegrid.js` + `calendar-sheet.js`, `warnings.js`, `settings.js`, pages `settings.html`, `upload.html`, `shortcut.html`, `pin.html`. Pure logic in `lib/` (shared with the Node tests): `photo-core` (fill crop and position), `caption-core`, `text-style-core`, `theme-core`, `layout-core`, `calendar-core`, `calendar-data`, `timegrid-core`, `fc-events`, `weather-core`, `settings-core`. Vendored: ical.js 2.2.1, FullCalendar 6.1.21 (`docs/THIRD_PARTY.md`). Targets Chromium 106. A minimal JS bridge (`addJavascriptInterface`) is allowed only for what HTTP can't do (video positioning, immediate events). The HA page (later) uses a separate WebView with no bridge.

## 4. Web UI hosting and dev mode

- The bundled UI ships in APK assets. If `/sdcard/OpenFrame/ui-dev/index.html` exists, the UI is served from that folder instead, with a "DEV UI" badge (`scripts/push-ui.ps1`).
- `POST /api/ui/reload` reloads the WebView.

## 5. Storage

```
/sdcard/FrameMedia/          user-visible, reachable over USB/MTP
  uploads/                   photos/videos sent from phones (§17)
    .incoming/               uploads in progress (ignored by the indexer)
  .trash/                    deleted files, kept 30 days (§15)
  test-synthetic/, test-samples/   development test media (keep)
  immich/, ha/               later (§20, §21)
```

- Any file copied into `FrameMedia/` (any subfolder) is picked up. Dot folders are skipped.
- **Removable volumes** (SD/USB): indexed **read-only**, whole drive or a configured subfolder; mount/unmount handled live. Rows of an unplugged drive stay in `media.db` as unavailable, so hidden flags survive re-insertion.
  - **FAT32 and NTFS** mount; **exFAT does not** (vold rejects it).
  - ADB and the USB port share **one controller**: a drive works only with the PC cable unplugged. `GET /api/diagnostics/storage` shows volumes and mounts over Wi-Fi.
  - Apps can't write to removable storage on Android 8.1, and this frame has no document picker (`com.android.documentsui` absent), so the frame never deletes there (§15).
- App-private: `config.json`, `config-history/`, `secrets.json`, `media.db`, `warnings-dismissed.json`, `calendar-state.json`, `cache/display/`, `cache/thumbs/`, `cache/calendars/`, `cache/weather.json`.
- Never write outside `FrameMedia/`, `/sdcard/OpenFrame/` (dev and diagnostics), and app-private storage.

## 6. Photo and video pipeline

Photos:

- JPEG, PNG, WebP. **HEIC can't be decoded on Android 8.1**: flagged and reported (§13), never a crash. Formats are detected by content (magic bytes), not extension.
- Display copy per photo: big enough to *fill* the screen in either orientation (short edge ≥ 1366 where the source allows), long edge ≤ **2048**, never upscaled, JPEG ~85%, EXIF orientation applied. One copy serves fit and fill in both orientations. A tiny pre-blurred background copy (~48 px) makes the blur background free.
- EXIF date taken and GPS are read. Truncated JPEGs (no end marker) are flagged. Files modified in the last ~5 s are skipped and rescanned. Failed items are retried after an app update.
- Smart fill crop: Android's `FaceDetector` (offline) centers the crop on faces, else the center. It finds **frontal faces only**, so a per-photo **position** (§15) overrides it per axis.

Videos (Phase 12, done 2026-10-14):

- **Decoders** (`/vendor/etc/media_codecs.xml`, read 2026-10-14): hardware `OMX.rk.video_decoder.avc` and `.hevc`, both **up to 1920×1088**; H.264 up to 1080p60 (489,600 blocks/s), HEVC up to **1080p30** (244,800 blocks/s); declared bitrate ≤ 10 Mbps.
- **Measured** (spike, 2026-10-14, synthetic clips): `MediaPlayer` here is Rockchip's own player (`RockFFPlayer`, in `mediaserver`), which drives the VPU directly and ignores those XML limits. Plays smoothly: H.264 and HEVC 1080p at 30 **and 60 fps**, HEVC at 12.4 Mbps, the Shortcut's video, portrait both native (1080×1920) and iPhone-style (stored 1920×1080 with a 90° flag; shown upright). **10-bit HDR fails** at once (error 1/−246 → skip). **4K "plays" without an error but the picture is corrupt**: the frame must refuse anything larger than 1920×1088 (either orientation) itself. A check at indexing (container, codec H.264/HEVC, size, 10-bit; `MediaExtractor`) lists the rest under "Can't be shown" with a plain reason ("4K: the frame plays up to 1080p"). Undecodable items get a warning, not a crash. Loop restarts take ~0.4 s.
- **Memory** (12 Mbps 1080p HEVC looping): app PSS unchanged (≈ 110 MB; decoding is in `mediaserver`), but MemAvailable drops ≈ 160 MB while playing (453 MB vs 615 MB after stopping).
- **The Shortcut's output** (first video upload, 2026-10-14 8:22 AM): MOV, HEVC Main 8-bit SDR (BT.709), 1920×1080 (reported as 1088), 30 fps, AAC sound, ~11.7 Mbps (above the declared 10 Mbps: test it first); **no date or location** (the conversion drops them).
- **Check and poster** (12a, built 2026-10-14): `VideoCheck` (pure, tested) refuses other codecs, larger than 1920×1088, 10-bit (HEVC profile ≠ Main, H.264 above High, read from the SPS in `csd-0`), PQ/HLG, and more than 1080p60's 489,600 blocks/s, with a plain reason pointing to the Shortcut (status `unsupported`, so updates don't retry it). The **first frame** (`getFrameAtTime(0)`, turned upright if needed) becomes the display copy, blur background, thumbnail, and face box, so Fit/Fill, Position, Automatic text color, the caption, and the Library work as for photos; slides and the Library carry `durationMs`; Library tiles show "▶ 0:21". ~1–3 s per video. `MediaIndexer.VIDEO_RULES` (now 2): when it changes, every video is processed again once.
- **Date and place** come from the file (`Mp4Meta`, pure, tested): this frame's `MediaMetadataRetriever` returns no date and "+0.0000-180.0000" for every video. Best first: the iPhone's QuickTime keys (`com.apple.quicktime.creationdate` with its offset, `…location.ISO6709`), then `udta/©xyz`, then `mvhd`'s creation time (0 = none). The Shortcut's conversion leaves only `mvhd` = the conversion time (the 8:22 AM video reads 8:22 AM), hence the date taken sent by the Shortcut (12d).
- **Native playback** (not HTML `<video>`): Android's `MediaPlayer` (no new libraries) on a `SurfaceView` **behind** the WebView, which is transparent over the video's box, so the clock, caption, menus, and swipes stay in the web UI on top. The box is placed through the JS bridge (device px) and follows rotation and Fit/Fill. **Proven** by the spike: the activity paints black, the WebView and the frame page (`html.frame`) are transparent, and only the video's rectangle is left unpainted; half-transparent web content (caption bubble, a 50% box) blends correctly over the moving video. The bridge (`window.OpenFrameVideo`: `play` returns a token at once, `move`, `pause`, `resume`, `setMuted`, `stop`) never waits for the main thread (the single-process WebView's drawing can wait for the page); events come back as an `ofvideo` DOM event (`started` at the first frame, `ended`, `error`). The player stops when the activity pauses (screen off, Android screen), on every page load, and when the WebView goes away.
- **Slideshow** (12b, built 2026-10-14; `slideshow.js`, `lib/photo-core.js` `mediaRect`/`visibleRect`/`holeClipPath`/`deviceRect`, tested): videos join the order when `video.include` (with a poster) and jump the queue when new, like photos. The poster cross-fades in like a photo; after the fade the native player starts behind it, and at its first frame the layer gets an even-odd `clip-path` window over the picture (`.ss.video-on`: no black behind it); the player's rectangle is rounded outward to device px. The next slide fades in over the playing or held video; then the player stops. **Playback**: Play once and continue (**default**, user request 2026-10-14) = about **1 s after the video ends**, ignoring the timer (measured: a 10 s clip hands over 13.1 s after it started, fade and photo load included); Play once and wait = moves on when both the interval and the video are over (holding the last frame); Loop = loops a video shorter than the interval until the interval ends. **A video is never cut off**. **A tap pauses it** (the quick menu opens; user request 2026-10-14, so it can be positioned without running on), and so do the full calendar and the editors (every `hold`); when they close it carries on, unless Pause was pressed in the menu (Position and Comment take the editor hold before the menu closes, so it doesn't run on in between; a pause asked for before the player is ready is applied at the first frame); hidden or asleep it stops. No first frame in 10 s, or no end 15 s past its length: skipped (and counted); a player error is skipped and counted; 2 failures list it under "Can't be shown" (status `error`, retried after an update). Measured: 10 s clip with a 30 s interval moves on after 31 s; 90 s clip after 98 s (with a 6 s calendar pause); Loop and Continue as described; paused under the calendar (0 frames), resumed after; a tap paused a playing clip at frame 81 and it carried on when the menu closed 10 s later; Position on a paused video kept it paused until Cancel; Pictures only full screen with the clock over it; ≈ 115 MB app PSS, MemAvailable ≈ 435 MB with a video loaded. Other browsers show the poster with a ▶ mark. Autoplay off: the poster with ▶; a tap plays it.
- **Settings → Photos → Videos** (12c, built 2026-10-14): Show videos (on); Autoplay (on; off = the poster with ▶, a tap plays it); **Playback** **Play once and continue** (default, user request: the next photo about a second after the video ends) / Play once and wait (Frameo's Play once: holds until the interval ends) / Loop; **Start with sound** (off: muted by default; the Sound button plays a video at the main Volume); **Auto-mute after 10 minutes** (off; no touch for 10 min → the playing video is muted within 30 s and new ones start muted until a touch); Volume → Sound. `config.json` → `video`: `include`, `autoplay`, `playback` (once/continue/loop), `muted`, `autoMute`; the slideshow gets them with every slide.
- **Quick menu** with a video on screen (frame): a row with **Play/Pause** (the tap that opened the menu paused the video, so it shows Play; Play restarts an ended video), **Sound off/on** (for that video and its replays), a **volume slider** (the main Volume; the frame likely has no volume buttons), and a **seek bar** (user request 2026-10-14: current time · bar · length; follows the video, polling `OpenFrameVideo.position` 4×/s; dragging scrubs, paused or playing; after a seek the bar keeps the dragged spot 1.5 s). Rockchip's player with a paused video (measured): a seek is reported done at once but performed only when it plays again, only the first since it last played, and not at all within ~1 s of where it is; its position echoes the request. So `VideoPlayer.seek` reaches the spot by playing muted up to it while watching the position: a little forward (< 2 s) just plays; a little back seeks 2 s before; farther seeks 0.5 s before; it stops 0.1 s past (display lag). One step at a time, latest spot wins; seeks never reported done count as done after 0.6 s. Measured: six probes within 0.07 s, drags within 0.04 s. Play continues from there; Sound on with the volume never set (or at 0) first sets it (the clicks' level, or 50%) so there is something to hear. Show as, Position, Comment, Hide, Delete as for photos. A user-paused video moves on 15 s after its length. Phones: the Library sheet plays the original (`GET /media/video/<id>`, byte ranges, PIN-gated; the frame shows the poster); the copy of the frame shows the poster with ▶.
- **Uploads** (12d, built 2026-10-14; §17): the upload page reads each video's size in the browser before sending and refuses larger than 1080p with a pointer to the Shortcut; the frame checks every uploaded video (`ImageProcessor.videoProblem`) and answers 415 with the reason, keeping nothing (tested: the 4K and 10-bit clips). Files on USB/SD or copied in are listed under "Can't be shown" instead. The Shortcut sends the **date taken and location** (`?taken=&lat=&lon=`; three Get Details actions and a longer URL; `/shortcut` and `docs/ios-shortcut.md` updated; **not yet tried on the iPhone**). Posters: if the first frame can't be read, three later tries (seen once, transient).
- Test clips (made 2026-10-14; the user's Shortcut videos too): `scripts/test-media/make-videos.ps1` (ffmpeg 9.0.2 essentials from gyan.dev, SHA-256 checked, in `Downloads\ffmpeg\`) → `test-video/` (git-ignored) → `FrameMedia/test-video/`: H.264/HEVC 1080p30, HEVC 12 Mbps, portrait (native 1080×1920 and iPhone-style rotated), 1080p60 both codecs, 4K, 10-bit HLG, 3 s, 90 s, silent, dated with GPS; each shows its name and frame counter and beeps every second.
- **Sound** (Phase 12, built first, 2026-10-14; `SoundController`, `GET /api/sound`, `POST /api/sound/test`; Settings → **Sound**, its own section after Display and sleep):
  - **Volume**: one main slider for every sound OpenFrame makes (videos; later Home Assistant chimes). It sets Android's **media** volume (0–15; videos; at 0 now, Frameo's "volume 0") and **system sounds** volume (0–7; keyboard and screen clicks; 5 now), so clicks move in coarser steps. Letting go of the slider plays a click to hear the level. No permission or root needed; the keyboard app is not touched.
  - **Click sounds** switch (user request): keyboard (LatinIME) and screen clicks can be off while the volume is on (system sounds at 0, media unchanged).
  - Tested with the user's OK: system sounds move together with the ring and notification volumes here (one alias); level 0 is silent, the ringer stays Normal, and Do Not Disturb stays off. Measured: 70% → media 11/15, clicks 5/7; Click sounds off → clicks 0, media unchanged.
  - Slider in steps of 5% ("Off" at 0); until it is first set it shows the clicks' current level. Letting go plays a 150 ms beep on the media stream (`ToneGenerator`), not while the screen is off. Changing Click sounds also saves the shown volume, so a never-set volume becomes set.
  - `config.json` → `sound`: `volume` (0–100; null = leave Android's levels alone until first changed, like brightness), `clicks` (on).
- **Smoother scrubbing** (2026-10-15, user request; was on the final checklist): each video gets a **preview strip**, one picture per second (longer steps beyond 100 s; at most 100 pictures), 180 px tall (320×180 for 16:9), side by side in one JPEG (~320 KB for 21 s), `files/cache/strips/<id>.jpg` + `.json` { v, count, stepMs, tileW, tileH, durationMs }. Made by `VideoStrip` when the video is indexed, before the slideshow hears of it (no two decoders at once for a new upload; ~5–6 s for a 21 s 1080p HEVC clip), or on first request (`GET /api/video/<id>/strip`; image `/media/strip/<id>.jpg`); deleted with the video; remade when `VideoStrip.VERSION` changes. While the seek bar is dragged the photo box shows the strip picture nearest the finger (`Slideshow.scrubPreview`, CSS background over the video's rectangle) and the player seeks **once, on release**; the preview stays until the player shows that spot (≤ 3 s). Without a strip (not made yet, or a video the decoder can't read) the bar seeks while dragging as before. Measured on the frame: a real swipe along the bar = 1 seek (was one per move); preview gone ~1.6 s after release; ≈ 118 MB app PSS, MemAvailable 597 MB.
  - Why not stills on demand: the frame's `MediaMetadataRetriever` (Rockchip's) ignores the requested time (the same first picture for every time, ~0.85 s each, sometimes none; measured 2026-10-15).
  - Rockchip's decoder output (measured): iPhone HEVC coded 1920×1088 comes back as an Image of 1920×1080 whose colour plane is placed after 1080 rows, but the decoder wrote it after 1088 (it still reports slice-height 1080); the first 8 colour rows are filler (value 100), which showed as a green band. `VideoStrip` skips that padding (decoder slice height when it reports a larger one, else the height rounded up to 16, converted to colour rows).
- Raw streams (`.hevc`, `.h264`) and other containers (`.mkv`, `.avi`) are flagged "needs MP4/MOV".

`media.db` → `media`: path, source (internal/removable), volume, type, mime, size, mtime, width/height, duration, taken_at, added_at, lat/lon, place, comment, hidden, fit_override, crop, face box, display size, rev, status (pending/ok/unsupported/too_large/error) + detail, available. Also `volumes`, `pending_comments` (upload comments waiting for indexing), `pending_settings` (fit and position of files restored from the Trash), `trash` (§15, with fit and position).

## 7. Slideshow

- **Order**: Shuffle (default), Date taken, Date added; **Reverse order** (off = oldest first).
- Shuffle shows every item once before repeating. **New items jump the queue** in every order mode; items found on a volume's first-ever scan are not "new".
- Order and position live in the shell (`/api/slideshow/current|next|prev`) and survive UI reloads and reboots. Only the frame's own WebView advances; other browsers mirror it.
- **Interval** 30 s default. **Fit** (default) or **Fill** (smart crop). **Background** around fitted photos: **blur** (default), black, or a color. Cross-fade transition (0–5 s).
- Swipe left/right = next/previous. **Tap = menu** (§15).
- While the page is hidden (screen asleep, an Android screen in front, another browser tab) the slideshow stops; it shows a fresh photo when visible again. Measured before this: 2 photos per minute were advanced and decoded while asleep.

## 8. Overlays

Clock and weather (`clock_weather` widget):

- Two styles: `panel` (block at the top of the Hybrid landscape column; white, dark in dark mode) and `overlay` (text over the photo, styled by §9).
- The overlay sits in a chosen corner (default **top right**) of the **screen** in Pictures-only and of the photo area in Hybrid portrait, never the fitted picture's edge. In the bottom-left corner it is lifted above the calendar button and status icons.
- `config.json` → `clock`: `showClock`, `showDate`, `showWeather`, `hour12` (default 12 h), `dateFormat` (long/short), `corner`, `size` (small/medium/large), `timeZone` (empty = the frame's), and the weather display options below; text font, color, and shadow are in `text` (§9). Re-renders once a minute.

Calendar button (Pictures-only): bottom left, opens the full-screen calendar. The status icons (§13) sit beside it; both are 60 px.

**Photo caption** (Phase 10, `caption` widget, `caption.js` + `lib/caption-core.js`), like Frameo's caption pill:

- A rounded dark bubble (white text, background darkness adjustable) with the photo's **comment**, **location** ("Place, Town" or the town; below), and **date taken** ("Oct 13, 2026"), each switchable. **Two lines** (default; comment on top, "Place · Date" smaller below) or **one line**. No bubble when there is nothing to show. Fades in with each photo; the comment is clamped to 3 lines, the bubble to ~58% of the photo's width.
- Corner setting (default **bottom left**). It moves to the other side when the clock overlay is in the same corner; above the calendar button in Pictures only; above the status icons in Hybrid only while they show (`has-status` class). Not in the Calendar preset. Text size small/medium/large (Medium confirmed on the frame); font, color, and bold from the text style (§9).
- `config.json` → `caption`: `showComment`, `showLocation`, `showDate`, `lines` (two/one), `corner`, `size`, `background` (0–1, default 0.45), `ignoreRadiusMi` (**8**, user decision), `ignoredPlaces` (≤ 20 `{ name, lat, lon }`).
- **Location**: EXIF GPS → city name **offline** (`PlaceIndex`): the bundled GeoNames list of places with more than 5,000 people (CC BY 4.0; `assets/geo/cities.tsv`, 64,505 places, built by `scripts/geo/make-cities.mjs`). The nearest place within 40 km, except that a bigger place within 1.5× that distance wins (outskirts of a city are often nearer a small neighbor's center). GPS of 0/0 or longitude ±180 (seen on a GoPro video) counts as none. `Places` fills `media.place` in the background (30 s after start, then after new photos; "" = nothing near) and releases the list after 2 min idle; loading it takes ~4.7 s on the frame, the first search ~6 s, later searches ~0.1 s.
- **Places left out** (user request): photos taken within `ignoreRadiusMi` miles of a listed place show no location (distance from the place's center, user decision). Picked in Settings → Photos → Photo caption by searching the bundled list (`GET /api/places/search?q=`). **Empty by default**; the user adds places as they see fit (user decision 2026-10-14). Tested: with a place left out at 8 miles, photos inside that circle lose the tag while one 12.6 miles out keeps it.
- **Precise place names** (2026-10-19; `PlaceNames` pure and tested, `PlaceLookup`): the caption reads **"Name, Town, ST"** (the town from the bundled list with the US state or the country code; 2026-10-19) (the name cut at 32 characters with "…"; only the name when it already holds the town, e.g. "Seattle Center"); no named place: just the town. The name comes from (1) the **iPhone Shortcut** (`&place=`, the location's Name, URL-encoded; kept in `sent_meta.place`, so it survives reprocessing; **it wins**, and no coordinates leave the frame for that photo; a name that is a street address, just the town, or a placeholder ("Location": what the Shortcut's Name detail sent for the user's photo on 2026-10-19, so it brings no names for now) counts as none; sending the same file again with a name updates it), else (2) OpenStreetMap, asked in the background ~2 s after `Places` names the town, **only for items with GPS and no precise name**, User-Agent "OpenFrame/<version> (Android photo frame)", coordinates to 5 decimals: first the **smallest named area the spot is inside**, else the **nearest within 25 m** (`PlaceNames.NEAR_M`, 2026-10-26: phone GPS is often 10–30 m off; a test photo landed 4 m outside a named building's outline) (church grounds, a park, a school, a named building such as the Space Needle, or a named retail, commercial, office or industrial building, which as land use are only zones (OpenStreetMap often tags a named shopping center building=retail); its `short_name` if it has one; at most 20 km²; never homes, neighborhoods, farmland, boundaries) from **Postpass** (Geofabrik's public OSM PostGIS, `postpass.geofabrik.de/api/interpreter`, one SQL query on `postpass_polygon` (bounding box, then `ST_DWithin` 25 m with the distance `d`; ## 10. Calendars (data)

- Source: Google's **"Secret address in iCal format"**, one link per calendar, any number. ICS because Google's device OAuth flow doesn't allow Calendar scopes and the frame has no Play Services or CalendarProvider.
- Per calendar: name, color (palette or custom), enabled, **show as "Busy"** (titles hidden; off by default), and optionally **your email in this calendar** (2026-10-16): events whose `ATTENDEE` with that address has `PARTSTAT=DECLINED` (per instance, so one declined meeting of a series) show with a crossed-out title in every view (`declinedBy`, tested). Google's feeds list every guest's answer but not which guest is the owner, hence the field. Lowercased; personal data, so never logged or put in chat. Metadata lives in `config.json` → `calendars` but changes only through `/api/calendars`; links go to `secrets.json` and are **never returned or logged** (the API shows `hasUrl` and the host). `webcal://` becomes `https://`.
- Sync every **15 min** (setting) with `ETag` / `If-Modified-Since`; a failed download never replaces a good cache. First sync ~5 s after start; a regained network triggers one. Status per feed: `ok` / `error` (+ `errorKind`: network, tls, http, parse, config; `failStreak`) / `never_synced`, last success.
- The shell keeps the raw download and serves a **trimmed** copy (`/api/calendars/<id>.ics`): unfinished recurring series plus single events from the last ~100 days. The revision changes only when the trimmed content changes, ignoring `DTSTAMP`.
- The UI expands recurrences with ical.js for the visible window only (`VTIMEZONE`, floating times, all-day/multi-day, `EXDATE`, `RECURRENCE-ID`, DST), fast-forwarding long series to just before the window (1–5 ms per ical.js step on this CPU).

## 14. Layouts and presets

## 16a. Web access PIN

- Any device other than the frame sees only the PIN page (`pin.html`, self-contained) until it signs in; every page, API call, photo, and calendar file answers 401 before that. Loopback requests (the frame's WebView, the shell, `adb forward`) never need it.
- No PIN set → other devices are **blocked**, and the page says where to set one.
- The PIN page matches the frame's light or dark look (2026-10-26, user report: it stayed light on the iPhone): the frame's page reports its look to the shell whenever it changes (`POST /api/ui/theme {theme}`, loopback only; Automatic is worked out on the frame), and the open `GET /api/auth/state` returns it as `theme` (before the first report: `theme.mode` when it is Light or Dark). The PIN page applies it and saves it as the browser's `of-theme`, so the upload and Shortcut pages after sign-in start in it too. Before, the page knew only the browser's own saved choice, which Safari clears.
- PIN: 4–8 digits, set and **shown** in Settings → System (stored readable in `secrets.json`; never exported or logged).
- Signing in sets an HttpOnly, SameSite=Strict cookie valid **1 day** (`<expiry>.<HMAC-SHA256>`). Changing the PIN rotates the key and signs out every browser (except the one that changed it).
- Guessing (`PinGuard`, unit-tested): 5 wrong PINs lock that address for 1 min, doubling per lockout up to 15 min; more than 30 wrong in 10 min from all addresses lock everyone for 5 min.
- Refused requests read and discard their body first, so phones get the 401 instead of a reset connection.
- Non-browser clients use keys instead: the iPhone Shortcut's **upload key** (§17); Home Assistant will get its own (§20).
- **Security check (2026-10-26, before V1.0.1)**: the PIN gate comes before every route except sign-in state, login, and keyed uploads; file routes take ids or reject `..`; upload names are cleaned to a base name; PIN, session cookie and upload key compared in constant time, keys from `SecureRandom`; the main WebView never leaves `127.0.0.1:8080`, file access off, debugging only in test builds; the web UI puts event titles, places, descriptions, comments and place names in as text (never HTML), so a crafted calendar invite can't run code; logs carry no links, coordinates, or keys. Fixed then: the **dev UI on shared storage is used only by test builds** (it would have run with the frame's own access), and every response says `X-Frame-Options: SAMEORIGIN`, `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff`. Accepted: plain HTTP on the home network (PIN and cookie unencrypted on the Wi-Fi; never forward port 8080 on the router), anything on the frame itself counts as the frame (loopback), and the factory `su` and USB debugging mean physical access is full access.

## 17. Photo upload

- `POST /api/upload?name=&comment=` with **the file as the raw request body**, one file per request (`Content-Length` required). It streams to `uploads/.incoming/`, so big videos never sit in memory. Answers: 201 saved, 200 duplicate, 401, 411 empty, 413 over 2 GB, 415 unsupported, 507 storage nearly full (300 MB kept free).
- Type from content: JPEG, PNG, WebP, MP4, MOV are kept; **HEIC/AVIF are refused** with "send it as JPEG"; audio and anything else refused. Videos the frame can't play (§6: larger than 1080p, 10-bit HDR, other codecs) are refused with the reason (Phase 12).
- `&place=` (2026-10-19): the location's name from the Shortcut (≤ 120 characters, kept in `sent_meta.place`; §8).
- `?taken=` (ISO 8601; also epoch seconds/ms and Shortcuts' default "Oct 14, 2026 at 8:22 AM"; a "+" lost in the URL is put back), `&lat=&lon=` (decimal degrees; 0/0 ignored): `UploadMeta` (tested), kept per path in `sent_meta` and applied after every processing of that file, winning over the file's own date and place (Phase 12, for the Shortcut's converted videos) — **except a photo's own EXIF date**, which wins over the sent one (2026-10-16: the user's Shortcut sent the first photo's date for a whole batch; photos uploaded before were processed again once, `photoOwnDates`). ## 18. Sleep, power, boot, and recovery

Sleep (`PowerController`; real Android sleep, a swipe wakes the screen, a tap doesn't):

- Screen off with `DevicePolicyManager.lockNow()` through a device admin whose only policy is `force-lock` (`SleepAdminReceiver`), no root. Activated with the user's approval: `adb shell dpm set-active-admin app.openframe/.SleepAdminReceiver`. Debug builds are `android:testOnly` (installed with `adb install -t`), so `adb shell dpm remove-active-admin app.openframe/.SleepAdminReceiver` always works; Settings → Display and sleep → **Turn off sleep** removes it from the app. An app with an active admin can't be uninstalled until it is removed.
- `config.json` → `sleep`: `schedules` (≤ 10; each `{ enabled, sleep: "21:30", wake: "07:00", days: [0–6] }`, 0 = Sunday) and `wokenTimeoutMin` (**5**). Default: **9:30 PM → 7:00 AM every day** (Frameo's sleep schedule). A day means the night that starts that day; wake-up is the same day if later, else the next morning; overlapping windows merge; a time skipped by DST moves forward (`SleepSchedule`, unit-tested).
- At sleep time the frame sleeps, unless it was touched within `wokenTimeoutMin`. **Woken during sleep hours** (swipe, or started inside a window), it sleeps again after `wokenTimeoutMin` without a touch (user decision 2026-10-13). At wake time it turns the screen on (`SCREEN_BRIGHT_WAKE_LOCK | ACQUIRE_CAUSES_WAKEUP`) and brings OpenFrame to the front (again 15 s later, in case Frameo's own schedule put itself on top).
- **Manual sleep** (quick menu, Settings, `POST /api/power/sleep`): until the next scheduled wake-up or a swipe; with no schedule, until a swipe (user decision).
- **Power** (2026-10-16, the one approved use of root, CLAUDE.md Safety rule 5): a Power chip after Sleep in the quick menu, **frame only** (not phones or the copy of the frame). It asks "Shut down the frame?" with **Cancel / Restart / Shut down** (a tap outside or 30 s without an answer cancels; the slideshow waits meanwhile), then shows "Shutting down…"/"Restarting…". `POST /api/power/off {action: "shutdown"|"restart"}`, loopback only (403 from other devices), runs `/system/xbin/su -c 'reboot -p'` or `su -c reboot` (`PowerOff`; SELinux is permissive, so su works from the app without a prompt); a failure (no su, non-zero exit, no shutdown within 15 s) comes back as a message on the frame. **Tested by the user 2026-10-16**: Restart works (back in about a minute); Shut down works, and plugging the frame in again does **not** start it: the power button on its back does. The question says so ("After Shut down, turn it on with the power button on its back"). The boot after it showed "--" until network time (`ClockTrust` logged the July 28 clock, then "Clock looks right"), and OpenFrame recorded no restart.
- **Power log** (user request 2026-10-19: a Shut down was not known to be on purpose): every press is kept in `power-log.json` (`PowerLog`, last 20: time, action, "requested" before the command runs, "failed: …" if it came back, and Android's boot count `Settings.Global.BOOT_COUNT`). `GET /api/system` → `power {last, startedAfter}`; `startedAfter` is true when this start is the one right after an accepted press (boot count + 1; the clock can't tell, there is no battery clock). Settings → System → Frame: "Shut down or restarted from the menu" (e.g. "Restart on Oct 19, 3:20 PM (this start came right after it)"). Tests: `PowerLogTest`.
- One exact `RTC_WAKEUP` alarm for the next boundary (sleep or wake), recomputed on config, time, and time zone changes.
- **At night the CPU stays up** (user decision): a partial wake lock while the screen is off, so uploads, sync, and later Home Assistant keep working. Android 8 disables wake locks of background apps, and with the screen off even the top app counts as background, so `FrameService` (a foreground service with an invisible notification, no status bar here) runs while the UI exists. Measured: the lock showed `DISABLED` without it.
- Schedules, the wake lock, and bringing OpenFrame forward act only while OpenFrame's UI exists, so a background OpenFrame process (Frameo as HOME) never takes over the screen.
- **Brightness** like Frameo (which stores 101 in `KEY_DISPLAY_BRIGHTNESS` = Android's `screen_brightness`): `config.json` → `display.brightness`, percent 5–100 of 0–255, or `null` to leave Android's value alone (default). Needs `WRITE_SETTINGS` (`adb shell appops set app.openframe WRITE_SETTINGS allow`, with approval). Set to 40% (102/255) in testing; Frameo's was 101.
- `GET /api/power` (admin, screen, manual sleep, window, next sleep/wake, brightness permission and system level), `POST /api/power/sleep|wake`, `POST /api/power/admin/remove`, `POST /api/power/off` (frame only).
- Measured 2026-10-13: **Frameo's own sleep schedule runs while Frameo's UI runs**, even behind OpenFrame. At 9:30 PM it started its `AScreenOffOverlay` activity on top of OpenFrame and slept the frame with a sleep key through a root helper; its slideshow then stayed on top. Its UI also holds a permanent partial wake lock. With OpenFrame as HOME, after a reboot Frameo's process runs (boot receivers) but its UI doesn't start, and neither the schedule alarms nor the wake lock exist. Starting Frameo's UI again re-arms them.

Boot and HOME (`HomeApp`):

- HOME is an `activity-alias` `.HomeActivity` → `MainActivity`, **disabled by default**: an enabled HOME filter changes Android's set of home apps, which drops Frameo's "always" choice (the chooser would appear on a frame with no navigation). Switched on with the user's approval: `adb shell pm enable app.openframe/.HomeActivity`, then `adb shell cmd package set-home-activity app.openframe/.HomeActivity`. Rollback in `CLAUDE.md`.
- `BootReceiver`: after boot, if OpenFrame is HOME (or Android would ask and the alias is on), bring OpenFrame forward at 15 s and 45 s, in case Frameo starts its UI. With Frameo as HOME it does nothing.
- Reboot test (2026-10-13, OpenFrame HOME, Frameo enabled): `FallbackHome`, then `app.openframe/.HomeActivity`; OpenFrame stayed in front; Wi-Fi reconnected; network time fixed the clock within ~30 s. The frame has **no battery-backed clock**: it boots with a stale date until network time arrives, so the schedule is re-evaluated on every time change (one harmless early "wake" alarm fired when the clock jumped). Booting during sleep hours counts as woken: asleep 5 min later. USB ADB needed the cable re-plugged after the reboot.
- **Before network time** (2026-10-16, user request: "no information is better than wrong information"): `ClockTrust` treats a time before this app's last install or the last time seen as right (saved every 10 min, 10 min slack) as wrong; `/api/status` reports `clockOk`. The frame checks it before its first draw and every 5 s until it's right; meanwhile the clocks show "--:--" and "--", the weather is hidden (its "today" needs the date), the day panel shows "--", and reminders wait. When network time arrives the day panel jumps to today. Photos and their own dates are unaffected; phones keep their own clock. Tested: `ClockTrustTest`, and on the frame by setting the page's flag (the frame's real clock is not changed).
- Settings → System → **Frame set-up** lists what should be in place before the user turns Frameo off: home app, sleep, brightness, return button, auto-rotate, automatic time, time zone, Frameo's state. Wi-Fi reconnecting without Frameo is checked with a reboot test.

Recovery (`CrashGuard`):

- Java crash: logged, recorded, and OpenFrame restarts after 3 s, 10 s, 30 s, 2 min, then 5 min while it keeps crashing within 15 min. Measured: `am crash` → back in ~1 s (Android relaunches the top activity), no "has stopped" dialog. The process ends itself rather than going through Android's crash handling, which shows "has stopped" and, for a non-system home app, **clears the home app choice**.
- Any other end (WebView renderer crash inside the process, low-memory kill): a watchdog alarm pushed back every 30 s while the UI exists restarts it within 90 s; usually Android relaunches the top activity at once (measured with `kill -9`: < 1 s). Recorded as "stopped unexpectedly" when the first UI of a fresh process is restored from saved state or launched as home > 5 min after boot, except within 2 min of an app update. Native crashes still go through Android's crash path, so with Frameo still enabled the home choice can be lost: warning (§13), and the watchdog brings OpenFrame back over the chooser.
- `am force-stop` cancels the alarms (the way back to Frameo still works). Restarts are kept in `restarts.json` (links stripped from messages) and shown in Settings → System.
- At 3:30 AM, if the screen is off, the UI reloads.
